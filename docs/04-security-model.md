# 04 · 安全模型

## 1. 首要原则

**SSH 的端到端安全不可被降级。** 隧道是 SSH 之外的一层额外封装：
即使隧道被完全攻破（攻击者成为中间人），攻击者得到的也只是 SSH 密文，
与直接在网络上抓包等价——SSH 的主机密钥校验与用户认证仍然成立。

隧道层安全的目标因此是**可用性与接入控制**，而不是机密性的最后防线：

1. 服务端不能变成任意 TCP 的开放中继（open relay）；
2. 攻击者不能劫持或干扰他人的 Session；
3. 被动观测者不应免费获得连接元数据（谁连了哪个内网端口）。

## 2. 信任边界与机制

| 风险 | 机制 |
| --- | --- |
| 客户端连到假服务端 | TLS 1.3（QUIC 内置）+ **SPKI pin**（`--pin sha256:<base64>`），或系统 CA + `--server-name`；用 SSH 密钥认证且未配 pin 时为 **TOFU**（`known_servers`，换钥即拒） |
| 未授权客户端接入 | **SSH 密钥**（服务端 `--authorized-keys`，authorized_keys 格式，支持 `cert-authority`；签名绑定 TLS exporter，见 §3.2），或**每设备一份 token**（服务端 `--credentials` 只存 `sha256(token)` + label + 可选有效期），TLS 内传输，常量时间比较 |
| 开放中继 | 服务端只连 `--target` 白名单；客户端 OPEN 里的 `target` 只是提示，不在白名单内即 RESET |
| Session 劫持 | `SessionID` 为 16 字节 CSPRNG，且**只能在通过 token 认证的 TLS 连接上使用**；猜中 ID 也需要有效 token |
| 旧链路抢占 / 重放 HELLO | `epoch` 单调递增，过期 HELLO 被拒（`EPOCH_STALE`） |
| 放大攻击 | QUIC 地址验证（quic-go 内置 Retry/token），不自行实现 |
| 资源耗尽 | `--max-streams`、每流窗口上限、Session linger 回收、握手超时 |

## 2.1 pin 与 token 的区别（最常被问到）

两者**都要配，缺一不可**，因为它们回答的是两个不同的问题：

| | `--pin` | `--token-file` |
| --- | --- | --- |
| 回答的问题 | 对面这台服务器**是不是我要连的那台** | 我**有没有资格**接入这台服务器 |
| 方向 | 服务端向客户端证明身份 | 客户端向服务端证明权限 |
| 本质 | 服务端**公钥**的指纹 | 预共享**密钥**（真正的密码） |
| 是不是秘密 | **不是**。可以写进文档、贴群里、提交到仓库 | **是**。文件权限必须 0600，否则服务端/客户端拒绝启动 |
| 泄露的后果 | 没有后果 | 别人可以接入你的服务端 |
| 类比 | ssh 首次连接让你确认的 `SHA256:...` 主机指纹（`known_hosts`） | 你的私钥 / 密码 |
| 何时校验 | TLS 握手期间 | TLS 建好之后，在加密信道里发 `HELLO` 时 |

### pin 是怎么算出来的

`pin = "sha256:" + base64(SHA-256(证书的 SubjectPublicKeyInfo))`

服务端启动时把它打印在日志里；客户端在 TLS 握手拿到服务端证书后自己算一遍，
对不上就断开（`internal/transport/tls.go` 的 `Pin` 与 `ClientTLS`）。
因为我们用自签名证书、没有 CA 背书，pin 就是取代 CA 的那个信任锚。

**pin 的是公钥而不是整张证书**：证书到期换发时只要密钥不变，pin 就不变，
客户端不用改配置；只有更换密钥才需要重新分发 pin。

### 两者的先后顺序很重要

pin 先生效，token 后发送。没有 pin（或用了 `--insecure`）时，中间人可以冒充服务端，
客户端会把 token 直接送到攻击者手上——**这就是为什么生产环境必须配 pin**：
它保护的不只是"连对机器"，还有 token 本身。

### 常见误区

| 误区 | 纠正 |
| --- | --- |
| "pin 是密码，要保密" | 不用。它是公开指纹，保密它没有任何安全收益 |
| "有 token 就够了，pin 可以省" | 省掉 pin 等于把 token 暴露给中间人 |
| "把 token 写进 `ssh_config` 里方便" | 危险。token 只放 0600 的文件，配置里只写路径 |
| "换证书就要换 pin" | 只要公钥没变就不用换，见上 |

## 3. 凭据与身份

服务端的 `--credentials` 文件每行一条，形态刻意对齐 API key 的常规做法：

```
# label            sha256(token)                                  not-after(可选)
laptop-mbp14       sha256:9f2b…                                    2027-06-01
phone-termux       sha256:c41a…
ci-runner-3        sha256:77de…                                    2026-12-31
```

- 客户端拿到的还是那串 token（`--token-file`，0600）；**服务端只存哈希**，
  所以服务端被攻破也拿不到可复用的凭据。
- token 是 32 字节随机数，熵足够，用 SHA-256 而非 bcrypt/argon2 那类慢哈希。
- 命中的那一行就是这条链路的**身份**（label）。它被用于：
  **会话绑定**（别的身份即使知道 `session_id` 也接管不了）、
  **每凭据配额**（`--max-sessions-per-credential`）、
  **审计归因**（日志里是 `credential=laptop-mbp14`）。
- 生成：`tingly-ssh keygen --label laptop-mbp14 [--expires 2027-06-01]`，
  它把 token 打到 stdout、把可粘贴进服务端文件的记录行打到 stderr。
- **撤销 = 删掉那一行 + `kill -HUP`**，不重启、不影响别人。
  文件解析失败时保留旧的一套，所以编辑时打错字不会把所有人锁在外面。

兼容性：文件里只写一个裸 token 时，仍按"单一共享凭据"工作（身份为 `shared`），
这是加身份之前的格式。此时服务端启动会告警，因为共享凭据没有身份、无法单独撤销、
日志也无法归因。裸 token 文件必须是 0600；只含哈希与 label 的文件不含秘密，不作此要求。

### 3.1 仍然存在的边界

- 凭据仍然是**对称秘密**：客户端要把它发给服务端。若客户端被骗去连了假服务端
  （没配 `--pin`，或用了 `--insecure`），这一份 token 就泄露了——但爆炸半径只有那一台设备。
  想让凭据完全不上线，需要 TLS 客户端证书，见 [ADR-0004](adr/0004-client-identity.md) §4，
  属于高保障场景的可选加强。
- **撤销不会踢掉已建立的链路**：凭据只在建链时校验。见 §7 的两条结论。

### 3.2 SSH 密钥认证（复用用户已有的钥匙）

设计全文：[`.design/ssh-key-auth.pencil.md`](../.design/ssh-key-auth.pencil.md)。要点：

- 客户端用 ssh-agent（或 `--identity` 指定的未加密私钥）签
  `SSHSIG("tingly-shell-hello-v1", "tingly-shell hello v1" 0x00 || TLS-Exporter || session_id)`，
  服务端用 `--authorized-keys`（OpenSSH authorized_keys 格式）判定。
- **凭据不上线**：线上只有绑定到本条 TLS 连接的签名。中间人把它转发到真服务端，
  exporter 对不上，验签失败。这正是 §3.1 里 token 做不到、ADR-0004 方案 B 想要的那一条。
- 因为不上线，未配 pin 时可以安全地**首次信任**服务端公钥；token 模式永远不走 TOFU。
- `SSHSIG` 魔数 + 专用 namespace：这些签名不可能被当成 SSH 登录签名，反之亦然。
  拒绝 `ssh-dss` 与 SHA-1 的 `ssh-rsa` 签名；`sk-*` 要求 user-presence。
- 身份是 `ssh:<公钥 SHA256 指纹>`（证书取内含公钥），日志 label 是注释或证书 KeyId；
  会话绑定、每身份配额、审计归因与 token 相同。
- 换网重连用服务端签发的**恢复凭证**（32 字节，服务端只存哈希，随会话消亡），不再调用 agent；
  客户端只把它出示给签发它的那把服务端公钥。重连时服务端仍按当前白名单复查那把公钥，
  所以**撤销语义与 token 相同**：删一行 + `SIGHUP` 后，该钥匙的会话无法再重连。
- 服务端**不读**任何用户的 `~/.ssh/authorized_keys`，也不读 `/etc/ssh` 的主机私钥。
  `from=` 选项会让整份文件加载失败：隧道无法替 sshd 执行它，不能让管理员误以为它生效了。

## 4. 密钥与证书管理

- 服务端首次启动若无 `--cert`/`--key`，生成 Ed25519 自签名证书并持久化到 `--state-dir`，
  在日志中打印 `pin=sha256:<base64(SHA256(SPKI))>`，供客户端配置。
- token 由 `tingly-ssh keygen` 生成（32 字节随机，base64），文件权限要求 `0600`，
  否则服务端拒绝启动（防止复制粘贴导致的全局可读 token）。
- 不做密钥轮转自动化：轮转 = 换文件 + 重启（会话会中断），记录在 roadmap。

## 5. 日志与隐私

- 默认日志不含 token、不含完整 `SessionID`（只打印前 8 hex），不含用户数据内容。
- `--log-level debug` 会打印帧头（类型、stream、offset、长度），不打印 payload。

## 6. 威胁模型：谁能做什么

| 角色 | 能做 | 不能做 | 靠什么挡住 |
| --- | --- | --- | --- |
| 被动观测者（抓包） | 看到 UDP 流量的时间与体量、两端地址 | 读取内容、伪造 | QUIC/TLS 1.3（含前向保密），外加 SSH 自身加密 |
| 在途主动攻击者 | 丢包、延迟、切断（可用性） | 篡改或注入字节 | TLS 记录完整性；改坏会让链路失败，会话层重放保证不丢不重 |
| **拿到 token 的人** | 建立新会话并连到 `--target` 白名单里的地址 | 冒充目标机、读取别人的 SSH 明文 | 白名单限制爆炸半径；SSH 自身认证仍要求私钥 |
| **被攻破的隧道服务端** | 流量分析（谁、何时、连哪个内网端口、数据量）、拒绝服务、记录元数据 | 读取或篡改 SSH 内容、冒充目标 sshd | SSH 端到端加密 + 主机密钥校验（`known_hosts`） |
| 被攻破的客户端主机 | 一切 | — | 隧道不改变这一点，SSH 私钥本来就在那台机器上 |

一句话：**隧道被完全攻破，等价于攻击者在网络上抓包**。他得到的是 SSH 密文，
主机密钥校验与用户认证照常成立。但隧道服务端是一个"位置"，元数据和可用性对它是敞开的。

## 7. 生命周期与有效期

| 对象 | 当前实现 | 默认值 | 到期/失效后 | 如何轮转 |
| --- | --- | --- | --- | --- |
| 凭据（token） | 每设备一份；服务端存哈希 + label + 可选 `not-after` | 32 字节随机 | 过期后握手被拒（原因为 `credential expired`） | 删一行 + `SIGHUP`，不重启、不影响其他设备 |
| `session_id` | 客户端生成的 128 位随机数，只存在于内存 | — | 进程退出即消失 | 不适用 |
| 会话（无链路时） | `--session-linger` 内保留状态等待重连 | 60s | 服务端 `CLOSE{timeout}` 回收，客户端放弃 | 不适用 |
| 会话（有链路时） | **无最大寿命**，可以活到进程结束 | — | — | 只能靠重启 |
| `epoch` | 每次重连 +1，内存态，用于拒绝旧链路 | 从 1 开始 | 随会话消失 | 不适用 |
| QUIC 链路 | 无活动即断 | idle 20s / keepalive 5s | 链路死亡，会话层重连 | 不适用 |
| TLS 证书 | 自签名 Ed25519 | **825 天** | 客户端握手失败 | 换证书；**只要不换密钥，pin 就不变**，客户端无需改配置 |
| 重放缓冲 | 对端 ACK 后立即释放 | 上限 = 每流窗口 | — | 不适用 |

两条必须知道的后果：

1. **撤销凭据不会踢掉已建立的链路。** 凭据只在握手时校验，一条活着的链路不会重新验证。
   撤销之后它无法再重连，但当前链路会一直活着；要立刻断开仍然只有重启服务端一条路。
2. **会话没有最大寿命。** 一个会话可以合法地存活数天，跨越任意多次重连，中间不需要再次提供
   任何新凭据（每次重连仍会带 token，所以撤销 token 能阻止**重连**，但阻止不了当前链路）。

### 7.1 服务端内存上界

会话数是内存的唯一放大项，所以它必须有上限：

```
最坏内存 = max-sessions × max-streams × 每流窗口 × 2      (发送重放缓冲 + 接收缓冲)
默认值   = 128 × 64 × 1 MiB × 2 = 16 GiB
```

默认值对一台专用小机器偏大，**请按实际并发调低 `--max-sessions`**。服务端启动时会把
这四个数字和算出来的上界打进日志，不需要自己算。超限时的行为：先驱逐"最久没有链路"的
会话（崩溃的客户端留下的僵尸不该挡住它自己重连），仍然没有空位才回 `RESOURCE_EXHAUSTED`，
客户端按退避重试而不是放弃。

## 8. 已知风险与处置

| 编号 | 风险 | 影响 | 现状 / 处置 |
| --- | --- | --- | --- |
| R-1 | **源 IP 被遮蔽**（已部分缓解：日志里有 `credential=<label>`，见 §3）：sshd 看到的是隧道服务端的地址，不是用户的 | fail2ban、按 IP 的审计告警、`Match Address` 规则全部失效 | 架构固有（RFC 8803 的 converter 同样如此）。缓解：隧道服务端日志记录 `session`/`epoch`/客户端地址并接入审计；目标机的暴力破解防护改用基于密钥与用户的策略。**跳板机场景尤其要注意：跳板机看到的将是 sidecar 的 IP** |
| R-2 | 会话隔离只靠 128 位随机 ID | 知道某个 `session_id` 的 token 持有者可以接管该会话 | **已修**：会话绑定到创建它的凭据身份，别的身份即使知道 `session_id` 且给出更大的 `epoch` 也被拒（`session belongs to another credential`）。仅在整个部署共用一个裸 token 时退化为原状态 |
| R-3 | 服务端没有会话数上限 | 持 token 的客户端可无限开会话；每会话最多 `--max-streams × (发送窗口+接收窗口)`，linger 期间断了链也占着内存 | **已修**：`--max-sessions`（默认 128），超限时先驱逐最久未连接的会话，仍满则回 `RESOURCE_EXHAUSTED`（可重试）。启动日志打印最坏内存上界。每凭据配额见 `--max-sessions-per-credential` |
| R-4 | **握手无速率限制** | token 暴力不可行，但可用于刷日志、耗 TLS 握手 CPU | 未修。修法：按源地址令牌桶 + 认证失败告警 |
| R-5 | token 无过期、无撤销、无标识 | 分不清是哪台设备在用；丢设备只能全员换 token 并停机 | **已修**：每设备一份凭据，带 label 与可选 `not-after`；撤销 = 删一行 + `SIGHUP`，不停机、不影响其他设备 |
| R-6 | 证书有效期 10 年 | 与 pin 模式不矛盾（pin 的是公钥），但不符合常规做法 | **已修**：生成的自签证书有效期 825 天；续期时保持密钥不变则 pin 不变，客户端无需改配置 |
| R-7 | `--insecure` 跳过证书校验 | 中间人可窃取 token | 启动时已告警；文档反复强调必须用 `--pin`。仅供本机开发。**用 SSH 密钥认证时此风险不存在**：签名绑定连接，中间人拿不到可复用的东西（§3.2） |
| R-8 | 隧道服务端是新增的对外暴露面（UDP 端口） | 一旦有远程漏洞即为入口 | 以非 root 运行 + systemd 沙箱 + 最小白名单，见 §9 |
| R-9 | 元数据对服务端可见：目标提示、会话数、时间与流量模式 | 可做流量分析 | 设计使然；日志默认不含 payload，只打印会话 ID 前 8 位 |
| R-10 | 重放攻击面 | — | 已缓解：TLS 1.3 提供前向保密；**0-RTT 未启用**，因此没有 0-RTT 重放问题 |
| R-11 | **ALPN `tingly/0` 在 ClientHello 里明文可见** | DPI 可以一眼认出"这是 tingly-ssh"，在受限网络里可能被针对性阻断 | 未修。修法：把 ALPN 做成可配置（例如伪装成 `h3` 与 HTTP/3 混流）。注意这只对抗协议识别，不提供额外机密性 |
| R-12 | **SNI 明文可见** | 泄露隧道服务端的主机名 | 未修。用 `--pin` 时其实不需要 SNI（pin 已完成服务端认证），可以加 `--no-sni` 省掉这个字段。服务端 IP 本来就可见，所以收益有限，主要对域名前置/抗审查场景有意义 |
| R-13 | **隧道服务端到目标机那一跳是普通 TCP** | 该段只有 SSH 自身的加密，隧道不提供额外保护 | 设计使然。部署要求：这一跳应在可信网络内（同机 loopback，或同机房内网）。跳板机场景里 sidecar 到跳板机的那一跳属于此列，见 `08-jump-host-topologies.md` §6 |

## 9. 传输层到底加了什么密

这一节回答一个容易被前面 §6 的措辞误导的问题：**隧道自己有没有加密？有，而且是强制的。**

### 9.1 两层独立加密

```
SSH 明文  ──SSH 自己的加密──▶  SSH 密文
                                  │
                        ──QUIC/TLS 1.3 加密──▶  线上的 UDP 包
```

- QUIC 不存在明文模式：RFC 9000/9001 规定它的传输层就是 TLS 1.3，`quic-go` 没有关掉的开关。
  连包头都有 header protection，包号是加密的。
- 我们的配置：`MinVersion: tls.VersionTLS13`、ALPN `tingly/0`、服务端证书 + 客户端 SPKI pin。
- 因此**路径上的攻击者看到的是双重加密的载荷**，token 也在加密信道里传输，只有服务端能看到。
- 前向保密由 TLS 1.3 的 ECDHE 提供；**0-RTT 未启用**，所以没有 0-RTT 重放面。

§6 里"隧道被攻破等价于抓包"说的是**端点**（终结 TLS 的隧道服务端）被攻破的最坏情况，
不是说线上是明文。即使那种最坏情况下，服务端看到的也只是 **SSH 密文**——
它读不到你的会话内容，这正是"SSH 端到端安全不可降级"的含义。

### 9.2 线上可见与不可见

| 线上可见（元数据） | 线上不可见 |
| --- | --- |
| 客户端与服务端的 IP 和端口 | 一切载荷：SSH 内容、目标地址提示、`session_id` |
| QUIC 版本、Connection ID | token（握手完成后才发送，在加密流内） |
| **TLS ClientHello 里的 SNI（明文）** | SSH 的版本 banner、认证过程、channel 结构 |
| **ALPN `tingly/0`（明文）** | 逻辑流数量、偏移量、重放行为 |
| 包长与时序（可做流量分析） | — |

最后两项分别是新记录的 R-11 和 R-12。

### 9.3 一个性能与安全的权衡（当前状态）

我们**没有**启用 TLS 会话恢复（没有设置 `ClientSessionCache`），所以每次重连都是一次
完整握手。好处是没有会话票据这类可关联标识、也不会误入 0-RTT 重放；代价是重连多花约
一个 RTT 加一次证书验证。换网时这一点会体现在"卡顿多长"里。
若要优化，正确做法是只开会话恢复、坚持不开 0-RTT，列入 roadmap。

## 10. 部署加固清单

- 客户端**必须**配 `--pin`；token 文件 `0600`（程序会拒绝更宽松的权限）。
- 服务端以专用非特权用户运行，systemd 片段至少包含：

```ini
[Service]
User=tingly
NoNewPrivileges=yes
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
CapabilityBoundingSet=
RestrictAddressFamilies=AF_INET AF_INET6
MemoryMax=512M
```

- `--target` 白名单只放真正需要的地址（跳板机场景就只放跳板机的 22 端口）。
- 防火墙只放行隧道的 UDP 端口。
- 日志接入集中审计：每条链路的 `session`、`epoch`、客户端地址都会打印，用于补偿 R-1。
- 轮转流程：
  - **证书**：保持密钥不变则 pin 不变，可随时换发，客户端无感；
  - **token**：在 M3 的多 token 支持落地前，轮转需要一个停机窗口。
