# ADR-0004 · 客户端身份：用 mTLS，而不是自研 HMAC 挑战-响应

- 状态：**提议中**（待确认；确认后改为"已接受"并进入 M3）
- 日期：2026-09-12
- 相关风险：`04-security-model.md` §8 的 R-1、R-2、R-3、R-5

## 1. 先把三件事拆开

"要不要做凭据身份的挑战"这个问题里其实混了三件事，它们的价值差别很大：

| | 要解决的问题 | 现状 | 价值 |
| --- | --- | --- | --- |
| **A. 不让密钥上线** | 密钥在传输中被窃听 | TLS 1.3 已经解决 | **低**，见 §2 |
| **B. 身份** | 服务端不知道是哪台设备在连 | 完全没有 | **高**，见 §3 |
| **C. 撤销与过期** | 丢一台设备要全员换 token 并停机 | 完全没有 | **高**，见 §3 |

通常说的"HMAC 挑战-响应"只解决 A。而我们真正缺的是 B 和 C。

## 2. 为什么挑战-响应基本是重复劳动

v0 的 token 是 bearer token over TLS 1.3，和 HTTP `Authorization: Bearer`、
Kubernetes ServiceAccount token 是同一个模型。TLS 1.3 已经提供：

- 服务端身份认证（我们还额外做了 SPKI pin，比公网 CA 更强）；
- 机密性与完整性；
- 前向保密（握手用 ECDHE，密钥不落地）；
- 没有启用 0-RTT，所以没有 0-RTT 重放面。

在这条信道里再套一层 HMAC 挑战-响应，能多挡住的只有一种情况：**服务端本身是恶意的，
想学到 token 去别处复用**。但服务端已经是被访问的那一方，它能做的事本来就是 token 授权的全部；
"去别处复用"这个问题的正确解法是**每个服务端一份凭据**，不是挑战-响应。

唯一剩下的场景是有人用了 `--insecure`：此时没有服务端认证，中间人可以窃取 token，
挑战-响应确实能保住 token 不上线。但这个口子的正确修法是别用 `--insecure`，
而不是为一个明确标注"仅供本机开发"的选项增加协议复杂度。

**结论：A 的收益接近零，不值得自研一套握手协议。** 自研握手还要自己处理 nonce 生命周期、
时钟、重放窗口、常量时间比较——这正是本项目一开始就决定不做的那类事（ADR-0003）。

## 3. 真正要的是身份，而身份能一次解四个风险

一旦服务端知道"这条链路是哪个客户端凭据建立的"，下面四条一起解决：

| 风险 | 有身份之后怎么解 |
| --- | --- |
| R-2 会话隔离只靠 128 位随机 ID | 会话绑定到创建它的身份；别的身份即使知道 `session_id` 也无法接管 |
| R-3 余下的每凭据配额 | 按身份限制会话数与内存，一个客户端打不垮整台服务端 |
| R-5 token 无过期/无撤销/无标识 | 凭据本身带标识与有效期，撤销 = 删一行，不需要动别人 |
| R-1 源 IP 被遮蔽 | 审计日志里记录的是设备身份，比"某个共享 token"有意义得多 |

## 4. 决策：身份用 TLS 客户端证书（mTLS）

不自研。直接用 TLS 已有的客户端认证，服务端维护一份**客户端公钥白名单**，
形态刻意对齐 SSH 的 `authorized_keys`：

```
# /etc/tingly/authorized_clients —— 每行一个客户端公钥 pin，# 开头是注释
sha256:AAAA...   laptop-mbp14      # 标识
sha256:BBBB...   phone-termux
```

- 客户端：`tingly-shell keygen --client` 生成自签名 Ed25519 密钥对，**私钥永不离开设备**；
  把打印出来的 pin 交给服务端管理员，和交 SSH 公钥完全一样的流程。
- 服务端：`tls.Config.ClientAuth = RequireAnyClientCert` + `VerifyPeerCertificate`
  比对白名单；匹配到的那一行就是这条链路的**身份**。
- 不建 CA、不做 PKI：用自签名证书 + 显式白名单，避免引入证书签发与吊销列表的运维负担。

### 为什么这比自研 HMAC 更省事

| | mTLS | 自研 HMAC 挑战-响应 |
| --- | --- | --- |
| 新增协议帧 | 0（TLS 层完成） | 至少 2（CHALLENGE / RESPONSE）+ 版本协商 |
| 密钥类型 | 非对称，私钥不出设备 | 对称，两端都持有同一份秘密 |
| 过期 | 证书 `NotAfter` 自带 | 要自己设计有效期字段与时钟处理 |
| 撤销 | 删白名单一行（配合 SIGHUP 热加载） | 要自己设计撤销列表 |
| 身份 | 天然有（凭据就是身份） | 要额外加字段 |
| 自研密码学代码 | 无 | nonce、重放窗口、常量时间比较 |

## 5. 与现有 token 的关系

token 不删，降级为**可选的粗粒度门禁**：

| 配置 | 行为 |
| --- | --- |
| 只有 token | 与今天完全一致（单机/小规模部署仍然最省事） |
| 只有 `authorized_clients` | 纯 mTLS，有身份、有过期、可单独撤销（**推荐**） |
| 两者都有 | 两者都必须通过 |

## 6. 代价与要处理的细节

- **密钥分发**：每台设备生成密钥、把 pin 交给管理员。对 SSH 用户是熟悉流程，但确实比
  "一份 token 抄两遍"多一步。
- **错误可读性**：客户端证书被拒发生在 TLS 层，客户端只会看到一个 TLS alert，
  拿不到我们的 `HELLO_ACK` 原因码。必须把这个错误翻译成人话
  （"服务端拒绝了本机的客户端证书：这台设备可能还没被授权"），否则会变成难排查的故障。
  这和我们修过的"拒绝原因必须能到达客户端"是同一类问题。
- **证书过期**：设备证书到期会直接连不上。默认有效期要足够长（对齐 825 天），
  并在客户端启动时对临近过期给出告警。
- **会话绑定的边界**：身份绑定后，同一设备重连仍然要能接管自己的会话（凭据相同即可），
  所以绑定的是身份而不是链路或地址——换网不受影响。

## 7. 被否决的替代方案

| 方案 | 否决理由 |
| --- | --- |
| HMAC 挑战-响应 | §2：在 TLS 之上收益接近零，却要自研握手与密码学细节 |
| 多 token（每设备一份，带标识与有效期） | 能解 B 和 C，但仍是对称秘密：服务端必须存明文或可验证摘要，泄露即冒充；比 mTLS 弱且代码量相近。可作为 mTLS 落地前的过渡 |
| 引入内部 CA 签发客户端证书 | 运维负担（签发、吊销、CRL/OCSP）远大于收益，我们只需要"认识这几台设备" |
| OIDC / SSO 集成 | 需要控制面与在线依赖，违背"自托管、单二进制、无控制面"的目标（`00-vision-and-scope.md`） |
